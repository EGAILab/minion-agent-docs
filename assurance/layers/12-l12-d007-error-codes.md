Coordination: `minion-agent#199`. Provenance, each finding keeping its own identity and closure evidence:
- #69 `L12-WINDOWS-ERROR-MAP`;

**Owner decision** (#69 / #125 / #67, "APPROVE OPTION 1: PINNED PI LITERAL ERROR CODES", sha256 `4ca7a5ca...b601`):
- For Pi-derived Layer 12 filesystem operations, the normative `FsErrorCode` is the code pinned Pi's `toFileError` returns for that operation, input and host platform. Correct §2.1 accordingly.

## 1. Method and safety

All probes run the **real** providers:
- pinned Pi's harness `NodeExecutionEnv` (`packages/agent/src/harness/env/nodejs.ts`, imported unmodified, Node v22.15.1 / libuv 1.49.2);
- Python's `LocalFileSystem` at `minion-agent` `origin/main` `319f5f3a`.

They use one condition × operation matrix: 16 Pi operations plus the 4 Minion-only primitives (EXEC-007/008/009). Each case runs in a fresh case directory.

**Containment** (Owner rule, 2026-10-10):
- Every probe creates its sandbox strictly under the project root (or, in the container, under a private tmpfs root).
- Every target, including rename destinations and the final cleanup, passes `assertInside` / `assert_inside` before every operation.
- An earlier version of this probe had a `bad-pathname` case whose `..`-chain target escaped to the drive root and ran destructive operations there. That case was removed and is **not** part of this evidence. Its rows, and all rows from runs before the guard existed, are discarded. Only the guarded runs above are credited.

**Disclosure on earlier runs:**
- Pre-guard runs showed 20 s operation hangs in the sharing-violation case. The guarded runs show none (every op ≤ 1 ms, `pi-busy-win32.json`), and Pi has no retry path (`nodejs.ts` `writeFile`: `mkdir -p` parent, then `fs.writeFile`). The hangs are attributed to the concurrent runaway deletion of the discarded case, not to Pi.
- Also discarded: the old `ntfs-stream-syntax` target `f:stream:bad` parses as **drive F:**. It now reads `./f:stream:bad`.

## 3. Where each Pi result comes from (pinned sources)

| Source | Version | Blob |
|---|---|---|
| libuv `src/win/error.c` (`uv_translate_sys_error`) | 1.49.2 (Node v22.15.1 `deps/uv`) | `7abf906bb5c82312aeb9f3f30f39ab2cadc07eae` |
| libuv `src/win/fs.c` | 1.49.2 | `f2215bb3082178193d37f8429536bfe7b707dd0d` |
| CPython `PC/errmap.h` (`winerror_to_errno`) | 3.13.5 | `a064ecb80b1ed93112ad9c275b6ac4037e7de423` |
| Rust std `library/std/src/sys/io/error/windows.rs` (`decode_error_kind`) | 1.97.1 | `3c2f41a90781314cbb4f7dc71baefc98387fc29e` |

Pi's `toFileError` (`nodejs.ts:97-121`) then maps:
- `ENOENT` → not_found;
- `EACCES` / `EPERM` → permission_denied;
- `ENOTDIR` → not_directory;
- `EISDIR` → is_directory;
- `EINVAL` → invalid;
- anything else → unknown.

**Win32 translation table (libuv `error.c`), the generic path:**

| Win32 | libuv errno | Pi code |
|---|---|---|
| 2 `FILE_NOT_FOUND`, 3 `PATH_NOT_FOUND`, 123 `INVALID_NAME`, 161 `BAD_PATHNAME`, 267 `DIRECTORY` | ENOENT | not_found |
| 5 `ACCESS_DENIED` | EPERM | permission_denied |
| 32 `SHARING_VIOLATION`, 33 `LOCK_VIOLATION` | EBUSY | unknown |
| 1921 `CANT_RESOLVE_FILENAME` | ELOOP | unknown |
| 206 `FILENAME_EXCED_RANGE` | ENAMETOOLONG | unknown |
| 1 `INVALID_FUNCTION` | **EISDIR** | is_directory |
| 87 `INVALID_PARAMETER` | EINVAL | invalid |
| 145 `DIR_NOT_EMPTY` | ENOTEMPTY | unknown |
| 17 `NOT_SAME_DEVICE` | EXDEV | unknown |

**Operation-specific overrides that come before the generic path:**

| Observation | Source |
|---|---|
| Write/append to a directory gives is_directory | libuv `fs.c` `fs__open` lines 576-581: `ERROR_FILE_EXISTS` with `O_CREAT` and without `O_EXCL` gives `UV_EISDIR` |
| Read of a directory gives is_directory | libuv `fs__open` opens with `FILE_FLAG_BACKUP_SEMANTICS` (line 566), so the open **succeeds**; `ReadFile` on the directory handle fails with 1 `INVALID_FUNCTION`, which becomes `UV_EISDIR` (`error.c:168`). Node's message: `EISDIR: illegal operation on a directory, read` |
| Non-recursive `mkdir` of an invalid name (123) or `ERROR_DIRECTORY` (267) gives invalid | libuv `fs.c` `fs__mkdir` lines 1224-1226: result forced to `UV_EINVAL` |
| `remove` (non-recursive, with or without force) of a directory gives unknown, on all platforms | Node's `rm` raises `ERR_FS_EISDIR` before any syscall; `toFileError` maps that unknown code to unknown (#125) |
| Over-long names give not_found on Windows (not ENAMETOOLONG) | **Not an override; the generic path.** `win32-codes.py` (a read-only `CreateFileW(OPEN_EXISTING)`, plain and `\\?\`-namespaced) shows the over-long single component (300 > 255) fails with **123 `ERROR_INVALID_NAME`**, not 206, exactly like `x<y` and `f:stream:bad`. 123 then becomes ENOENT, so not_found. (206 would be unknown; the matrix does not reach it.) |

## 5. Scope boundaries

- **Parity surface:** the 16 Pi-derived operations (`readTextFile`, `readTextLines`, `readBinaryFile`, `writeFile`, `appendFile`, `renameFile` source and destination, `fileInfo`, `exists`, `listDir`, `canonicalPath`, `createDir` recursive and non-recursive, `remove` plain / recursive / force) on both platforms.
- **Preserved, not parity:**
  - EXEC-007/008/009 (`list_dir_raw`, `probe_dir_entry`, `check_readable`, `check_read_write`) keep their own specified dispositions (§11-§13).
  - `not_supported` capability answers keep theirs.
  - The primitive columns are recorded for information only.
- **No global remap:** errno / `InvalidInput` / `ErrorKind` are never remapped wholesale. Translation is keyed on the **original Win32 code** of the failing call, plus the named per-operation overrides of §3, in Layer 12's Pi-derived filesystem operations only.
- **Rust:** the Rust owner characterizes Rust against the same tables. This record does not use Rust behavior as an oracle.
