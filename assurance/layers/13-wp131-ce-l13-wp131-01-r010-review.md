## Blocking findings

### L13-WP131-R010-A — proposed message replacement requires owner governance

**Classification:** `PI_PARITY_DEFECT` in the proposed contract unless explicitly governed as an
intentional divergence.

Layer 12's `FsErrorCode` is an internal capability-seam normalization. It does not authorize Layer
13 to replace a higher-level tool's observable error messages. Pinned Pi's stable authored strings
are coherent branch-specific behavior even though adjacent branches expose raw platform messages.
“Mixed” does not mean “non-contractual.” Tool failure text reaches the model through the normal
tool-execution error result, so a new Layer-13 template is observable.

Minimal discriminating witness:

```text
setup
    ls(path="/missing") and ops.exists("/missing") -> false

pinned Pi
    rejects with exactly "Path not found: /missing"

proposed contract
    permits a newly-authored not_found template whose wording need not equal Pi's

distinction
    the model-visible tool error text differs while TOOL-028 remains disposition=adopted
```

The same issue applies to `Not a directory: ...`, `Cannot read directory: ...`, and `Operation
aborted`. Cross-provider variability in the embedded/raw suffix does not erase the stable wrapper
and branch structure Pi itself authors.

**Required correction:** present an owner-facing decision matrix rather than a single automatic
resolution. At minimum:

1. a Pi-structural option preserving the stable authored templates/wrapper exactly and preserving
   the underlying provider message on raw/hybrid branches; and
2. the proposed closed Layer-13 template vocabulary, explicitly classified as an intentional,
   model-visible divergence with its fidelity/portability tradeoff.

Do not mark option 2 adopted merely because it consumes an adopted lower-layer error code.

### L13-WP131-R010-B — FsError mapping table omits reachable classifications

**Classification:** `CONTRACT_ASSURANCE_DEFECT`

The table says an `ls` top-level `stat` failure and `readdir` failure map only to
`permission_denied`/`unknown`. That is incomplete relative to both the artifact's own TOCTOU
description and certified section 2.1:

- `ENOENT -> not_found` is reachable when the path disappears after `exists` or before/during
  `readdir`;
- `ENOTDIR -> not_directory` can arise from a changed/non-directory path component;
- `EINVAL -> invalid` remains part of the certified mapping; and
- other mapped conditions must not be collapsed into `unknown` merely because the Pi message is
  raw or wrapped.

Minimal discriminating witness:

```text
ops.exists(path) -> true
ops.stat(path)   -> directory
ops.readdir(path) throws an ENOENT-shaped failure

pinned Pi message shape
    "Cannot read directory: <underlying ENOENT message>"

certified Layer-12 classification
    not_found

candidate table
    lists only permission_denied / unknown for this branch
```

**Required correction:** enumerate each reachable certified `FsErrorCode` for the raw `stat`, raw
`read`/`access`, and hybrid `readdir` branches, or state a general rule that preserves the exact
underlying `FsError.code` without pretending the branch has only two possible codes. The decision
matrix must say whether a separate tool-stage label such as `enumeration_failed` supplements or
replaces that underlying cause; replacement loses information and must be disclosed.
