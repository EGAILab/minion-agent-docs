== Why a v2 run was needed ==

Integrating R006-C into TOOL-028 raised two questions the v1 differential did not cover.

1. Normalization. v1 left UCOL_NORMALIZATION_MODE at ICU's default (OFF), because the pinned
   options list only the Intl.Collator-level settings. Pi's comparator is
   a.toLowerCase().localeCompare(b.toLowerCase()) (ls.ts:155). Probed on this host (Node 22.15.1,
   ICU 76.1, en-001): localeCompare returns 0 for four canonically-equivalent pairs, three of them
   non-FCD (combining marks out of canonical order). Probed on the pinned ICU 78.3
   (results/norm_probe.log): with NORMALIZATION OFF those three pairs compare -1; with
   NORMALIZATION ON all four compare 0. So the v1 settings do NOT reproduce Pi on an en-001 host
   for such names, contradicting the owner decision's own parity disposition. ECMA-402 requires
   canonically-equivalent strings to compare equal; NORMALIZATION_MODE=ON is the ICU attribute that
   delivers it. Classification: CONTRACT_ASSURANCE_DEFECT in the option mapping (not a change to
   the owner-selected Intl-level options).

2. Case mapping. Lane C revision 4, Correction 2, found real Unicode-version skew in the
   toLowerCase step across runtimes and required it to be pinned or disclosed. v1 lowercased once
   in the harness (Python str.lower) and fed both engines the same strings, so it proved the
   collator only. v2 lowercases INSIDE each engine with ICU root-locale full case mapping from the
   same pinned build (PyICU UnicodeString.toLower(Locale.getRoot()); Rust u_strToLower with locale
   "" via rust_icu_sys 5.8.0). ECMA-262 defines toLowerCase as Unicode Default Case Conversion,
   which ICU's root-locale lowercase implements. No crate beyond the pinned tuple is used.
