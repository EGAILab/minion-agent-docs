## 1. Method and safety

Both probes run over one matrix, `data/l12-d008/div008-matrix.json`:
- 13 controlled rows, with injected failures at the binding's real seams;
- 2 natural Linux rows × 10 runs, using real `EACCES` from directories `chmod 0555`, as uid 1000.

**`div008-pi-probe.mjs`** runs pinned Pi's real `NodeExecutionEnv.remove`, imported unmodified.
- It intercepts the callback-API `fs` calls that Node's `rimraf` makes.
- It **holds** the injected failures until all are pending, then delivers them **in the row's settlement order**, one macrotask apart.
- It records:
  - every intercepted call, with each settlement, in order;
  - the calls and remaining entries **at the moment `remove()` settles**;
  - the same **after every in-flight operation has drained**;
  - the calls made after settlement (`late_calls`).

**`div008_py_probe.py`** runs Python's real `LocalFileSystem.remove` with the same injections (the CE-02 seams). It records its own traversal. Python is sequential, so the settlement order does not apply.

Every fixture write, `chmod` and cleanup goes through the reviewed fs-guard (CE-L12D007-01), in sandboxes inside the project root. On Linux that is the container's private tmpfs.

The original `#127` probes (`data/l12-d001/ce/multi/`) are **preserved unchanged** as history. They made their sandbox under the system temp directory, so they are not rerun under the 2026-10-10 containment rule.

**`div008_compare.py`** applies the rule (§4). Its `--self-test` rejects six synthetic violations.

**Findings:**
1. **Selection.** Pi reports the first failure **to settle**: M2, M4, M6, M8 and M10 flip with the settlement order, and the code follows the selection (M4: `unknown`). Python reports the first failure **in its traversal**. That is host enumeration order: alphabetical on NTFS, reverse creation order on Linux tmpfs. This is DIV-008's subject, and is as the Owner decided.
2. **Extent.**
   - Pi's `_rmchildren` starts every child's removal before any settles (pinned blob `24bf3f46`, lines 144–158). Its drained state is therefore deterministic: **every removable entry is gone**. In these rows exactly the failing entries and their ancestors remain, in every row and in all 20 natural runs. *(Corrected in §7: this composition holds only when no failure prevents entering a subtree. A listing or first-`rmdir` failure keeps the unvisited subtree; see rows B1–B7.)*
   - Python at `e681c22f` stops at the first failure (§19.5 rule 4 as certified by L12-D007), so siblings after it remain. That happens **with a single failure** too (S1/S3 on Windows, S2 on Linux), and in N2 on all 10 runs.
   - The old `#127` note "Pi and Python both removed every sibling" described Python before L12-D007 and no longer holds.
   - This evidence went to the Owner, who decided **"Continue siblings"** (`#215` issuecomment-6118734550).
3. **Timing.** Pi can return **before** its other removals finish. In S1, `tree/b` was still present when `remove()` settled; its `unlink` ran afterwards (`late_calls`), and `tree/b` was gone after the drain. In N2, run 5, a late `unlink tree/z/locked` was recorded.

## 3. Assurance observation on L12-D007's CE-02 evidence

The CE-02 probes (`data/l12-d007/ce02/`) snapshot the remaining entries **when `remove()` settles**, before Pi's late removals. Their "remains MATCH" results therefore show agreement with Pi's **settlement** state, not with its **drained** state. S1 above shows that the two can differ.

This does not reopen L12-D007's certified rules (routing, classification, recovery, error identity). Extent is DIV-008's subject. L12-D008 measures the drained state, and §19.5 rule 4 is amended to require it.

## 4. Contract

- **§19.5 rule 4, as amended:**
  - siblings continue past a failure;
  - a directory with a failed descendant is not removed;
  - the first failure **encountered** is reported, unchanged;
  - when `remove` returns, the drained state of pinned Pi remains. *(As corrected in §7, its composition is: a failed entry with its ancestors, and the whole unvisited subtree of an entry that could not be entered.)*
- **§20:** the delta, with the authority, the rule and the evidence.
- **DIV-008** in `assurance/pi-divergences.md`: it covers **selection and timing only**.
- **Manifest:** row `EXEC-002-DIV-008`, disposition `intentional divergence`.

**The comparator rule** (`div008_compare.py`), per row and run:
- **EXTENT:** what the binding leaves equals pinned Pi's `after_drain` state;
- **COMPLETE:** no binding-only unfired injection (no skipped sibling), and no late calls;
- **SELECTION:** the binding's path is the first `settle` in its own sequence, and its code is that failure's. A row where this differs from Pi is reported as `DIV-008`, never as a match;
- **OUTCOME:** ok or failed agrees with Pi.

Applied to the pre-change binding (`e681c22f`), it **rejects 12 Windows rows and 21 Linux row-runs**, all on extent or completeness. So it separates the two rules on real outputs, not only on synthetic ones.

## 5. Python candidate

**The change** (`execution/filesystem.py` `_rimraf`): the explicit-stack walk (L12D007-I005) keeps a per-directory `failed` flag.
- A child failure records the first failure, marks the directory, and the walk continues.
- A failed directory skips its final `rmdir` and marks its parent.
- The first failure is raised at the end.

No call sequence, classification, recovery or error mapping changes.

### `L12D008-C001` (high): the extent claim was over-generalized

The contract said that when `remove` returns, "exactly the failing entries and their ancestors remain". The reviewer's witness disproves this. If listing `tree/a` fails (with `tree/a/x` inside and a removable sibling `tree/b`), pinned Pi and Python **both** keep `tree/a/x`. It is neither a failed entry nor an ancestor of one. The cause: all 13 controlled rows failed a leaf `unlink` or an empty directory's `rmdir`, and the natural directories stayed listable. The special case was generalized beyond its domain.

**Remediation:**
- **Extent composition corrected** in spec §19.5 rule 4 and §20, in the DIV-008 registry, the manifest row, and §§2 and 4 above. The composition:
  - every reachable removable entry is gone;
  - a failed entry remains with its ancestors;
  - an entry that could not be entered keeps its **whole unvisited subtree** (a failed listing, or a first `rmdir` that fails with a non-descending error);
  - a failed final `rmdir` keeps the emptied directory.

  The comparison point stays pinned Pi's drained state. No production change was needed; the walk already behaved this way.
- **Boundary rows B1–B7 added** to the matrix: a child's listing, classification, first `rmdir` and final `rmdir`, each with a removable sibling; and the target's listing, first `rmdir` and final `rmdir`. Pinned Pi and Python agree on all seven, on both platforms:

| Row | Pi = Python (both platforms) | What remains |
|---|---|---|
| B1 child listing fails | `permission_denied` at `tree/a` | `tree/`, `tree/a/`, `tree/a/x` (the subtree is kept; `b` is removed) |
| B2 child classification `lstat` fails | `ok` (rule 1: unlinked as itself, then removed) | nothing |
| B3 child first `rmdir` fails | `permission_denied` at `tree/a` (no listing) | `tree/`, `tree/a/`, `tree/a/x`; Pi removes `b` late |
| B4 child final `rmdir` fails | `permission_denied` at `tree/a` | `tree/`, `tree/a/` |
| B5 target listing fails | `permission_denied` at `tree` | everything |
| B6 target first `rmdir` fails | `permission_denied` at `tree` | everything |
| B7 target final `rmdir` fails | `permission_denied` at `tree` | `tree/` |

- **Python witnesses:** the 7 rows are in the oracle `div008_pi.json` (now 20 rows) and in `test_filesystem_remove_multi_failure.py`. Its `_violations` now also checks the outcome against Pi, and selects nothing for a recovered (`ok`) row such as B2.

### `L12D008-C002` (medium): the comparator did not enforce all it claimed

The comparator had two gaps. It accepted a **wrong code for the correct own-first failure**, and it accepted **undrained or incomplete evidence**. The reviewer observed both directly: M3 with `result` changed to `not_supported`; `drained=False`; `settle_incomplete=True`.

**Remediation in `div008_compare.py`:**
- **Readiness first.** An oracle row that did not drain, settled by the timeout, or left an injection unfired is **INVALID**. So is a binding row that did not drain. Such a row is never compared, never counted, and fails the run.
- **Code check.** The selected failure's code must be the matrix's `codes` table entry for the injected code. The table itself is checked against pinned Pi's own reported code wherever Pi selected that failure, so it cannot drift from the oracle. DIV-008 permits a different failing **entry** with **its** correct code, never a different code for the same selection. Natural rows require the binding's code to equal Pi's for the same host failure.
- **Self-test:** 13 controls, each credited only on its intended verdict **and** reason:
  - the positive;
  - a false first-settled claim;
  - a wrong code;
  - Pi's code borrowed for the own-first failure;
  - a skipped sibling;
  - an extent difference;
  - late calls;
  - an outcome difference;
  - an undrained binding;
  - an undrained oracle;
  - a timeout-settled oracle;
  - an unfired oracle injection;
  - a code table that disagrees with Pi.
- **`--controls`, on real rows:** the unmodified baseline must pass first. Then an actual candidate M3 row must FAIL with a wrong code, and with the other injection's code. It must be INVALID when the binding is undrained, the oracle is undrained, or the oracle is timeout-settled. Result: 5/5.
