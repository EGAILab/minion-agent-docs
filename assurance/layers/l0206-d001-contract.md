## 3. Canonical evidence

**Authority.**
- `data/l0206-d001-k1/` (`harness/run.sh`): `make_cases.py` produces 28 cases, which `k1_boundaries.mjs` runs to give `out/k1-boundaries.json`. `k1_probe.mjs` produces `out/k1.json` (characterization, unchanged).
- Pinned sources are checked by `pi_sources.sha256`, and typebox 1.3.7 by `acquire_npm_pinned.sh`.

**Corpus.**
- `minion-agent` `conformance/agent/key-order/key-order.json` (`key-order-scenario.schema.json`) has 28 cases, generated by `harness/make_scenarios.py`. It observes `raw`, `replay`, `hook` and `execute`.
- It covers:
  - insertion-only, index-only (ascending, reverse, numeric versus lexicographic), mixed and interleaved keys;
  - the index boundaries `0` and `4294967294` against `4294967295`;
  - non-canonical numerals (`00`, `01`, `007`, `-0`, `-1`, `+1`, `1.0`, `1e3`, ` 1`, `1 `, `0x1`);
  - large numeric strings; duplicates; `__proto__`;
  - nested objects, deep nesting, objects in arrays, the empty object;
  - declared schemas (`{z, a}`, extras, an index property, nested);
  - hook mutation (a new index key, an overwrite plus a new index key);
  - Minion hook replacement;
  - `edit`'s prepare shim.
- **Dropped from the canonical set:** coercion. Pi's `Value.Convert` keeps positions (`k1.json`), but Minion's validator does not coerce (the `TOOL-003` mapping), so such a case would test validation, not order.

**Runner.** The runner is thin. `tests/conformance/key_order_runner.py` builds the insertion sequence by plain assignment and observes; ordering is the pipeline's job.

**Current Python binding:** fails **22 of 28**. Every failure is order (insertion order), at `raw`, at `hook` (`edit`) or at `execute` (mutation, replacement).

## 4. Negative controls (with the implementation)

Each must fail the corpus, while the conforming implementation passes:

| Control | What it does |
|---|---|
| insertion order | the binding as it is today |
| sorted order | Rust's prepared `BTreeMap` today |
| declared-schema order | the pydantic `model_dump` behavior, applied to a raw-schema tool |
| top-level only | nested objects keep insertion order |
| a non-canonical numeral as an index | for example `"01"` or `"4294967295"` ordered as indices |
| ordered at construction only | a mutation appends |
| ordered before persistence only | replay returns insertion order |

## 5. Python (after the checkpoint)

**Implementation intent**, for checkpoint review. The mechanism is the binding's (decision §4).
- **An ES-ordered mapping.** A `dict` subclass, or an equivalent, whose iteration, `keys`, `items`, `values`, `repr`, equality order and JSON encoding enumerate by the rule. It is applied recursively to nested objects.
  - It is created at `ToolCallBlock` construction, at session decode, on `prepare_arguments` and validation results, and on hook replacements.
  - Assignment keeps the rule: a new index key goes to its ascending position.
- **The typed-model path (K1-F1):** keys present in the validated input, in input order; then the defaulted keys, placed by the rule.

## 6. Rust (NOT_IMPLEMENTED)

- The raw `IndexMap` and the prepared `BTreeMap` both need an ES-ordered object representation (or ES enumeration at every observation point), applied recursively.
- Rust must pass the 28 cases and Rust equivalents of the §4 controls.
- The type design is Rust's.
