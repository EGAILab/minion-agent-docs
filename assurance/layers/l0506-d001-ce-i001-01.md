# CE-L0506-D001-I001-01: pydantic declared-type characterization (convergence episode)

- **Coordination:** `minion-agent#88`, state CONTRACT_CONVERGENCE.
- **Trigger:** A. `L0506-D001-I001` survived two independent reviews: `#200` comment `5913924339`, then `#90` comment `5918098742`.
- **Purpose:** characterize the bounded pydantic declared-type / composed-branch surface, and agree a checkpoint **before** another patch.

No code change accompanies this record.

## Root cause of the surviving defect

Both earlier mechanisms judged a union **after pydantic had already chosen a branch**:
- the JSON-schema filter;
- the declared-type walk over the *validated* instance, which picks the first union member whose outer Python class matches.

A validated value no longer carries the alternatives. For example, with `list[float] | list[Any]`, `[inf]` is just a list, so the walk tries `list[float]` first and rejects. Pi's `anyOf` accepts it, because some alternative accepts the complete value. The same flaw hits `Inner | dict[str, Any]`: pydantic returns an `Inner` instance, and the `dict` alternative is lost.

## Candidate mechanisms, characterized

1. **Force `allow_inf_nan=False` into the model's pydantic-core schema.** Rejected by evidence. pydantic-core honors the flag on `float`/`nullable` nodes but ignores it inside a `model` node, whatever the node's `config` or `ref` (pydantic 2.13.4 / pydantic-core 2.46.4).
2. **Walk the validated instance.** Rejected. It is branch-lossy, as above.
3. **Proposed: a finite variant of the model, validated by pydantic itself.**
   - The variant has the same field names, `FieldInfo` (aliases, defaults), config, validators and base.
   - Every `float` occurrence in a field annotation is rewritten, recursively, to `Annotated[float, pydantic.AllowInfNan(False)]`. The rewrite goes through unions/`Optional`, `Annotated` (metadata kept), `list`/`tuple`/`set`/`dict` arguments, nested `BaseModel` classes (built as finite variants too), `TypedDict`s and dataclasses.
   - Validation of the prepared arguments is otherwise unchanged. The original model's validation result is returned, so pydantic coercion is unchanged.
   - The finite variant then validates the same prepared arguments. Only a failure of the variant rejects the call, as Layer 06's argument-validation error.

   pydantic's own union semantics (smart mode, every branch tried against the complete value) then decide: a non-finite value is accepted exactly when some finite-only alternative accepts it. That is Pi's `anyOf` behavior. The mechanism does no first-match, sweep or outer-class guessing.

### Root cause of both findings

The rev-1 mechanism ran the finite rule as a **second pydantic validation of the input**, through a variant that inherited the model's validators.
- **C001.** Every user validator ran twice, so a one-shot or side-effecting validator changed an ordinary finite call.
- **C002.** `AllowInfNan(False)` checks the input before an after-validator can produce a non-finite value. That value then passed.

### Revised mechanism: the delivered-value shape check

1. **One ordinary pydantic validation.** `model.model_validate(arguments)` runs exactly as certified Layer 06 runs it: each user validator once, in pydantic's order, with its own result. Nothing else validates the input.
2. **The delivered value is judged.** `delivered = model.model_dump()` is the exact value handed to the before-hook and `execute()`, as today.
3. **Two callback-free structural shapes of the declared types** are built once per model:
   - `float` is finite-only (`AllowInfNan(False)`) in the *finite* shape and plain in the *open* shape;
   - `str`/`int`/`bool`/`bytes`/`None`/`Literal`/`Any`/`object` are kept as declared;
   - unions and generic containers go through their arguments;
   - `NewType`, `type` aliases and `RootModel` are shaped as their underlying type;
   - every record type (model, dataclass, TypedDict) becomes a shape model over its **delivered keys**. Those keys are field names, or serialization aliases under `serialize_by_alias`, plus computed fields with their declared return types. Every key is optional (an excluded field is absent), and extra keys are allowed (undeclared);
   - any other class is checked by `isinstance` alone.

   Nothing that can run user code is copied: no `Annotated` metadata (validators, constraints), no decorators, no defaults and no custom schemas. Recursive and mutually recursive records resolve through forward references.
4. **Reject iff** `delivered` fits the open shape but not the finite shape.
   - Pydantic's smart-mode union semantics decide, against the complete value. A non-finite value is kept when some finite-only alternative accepts it (Pi's `anyOf`), so an `Any`/`object` alternative or an undeclared extra keeps it.
   - A delivered value outside the declared shape altogether is not a declared numeric position, and stays pydantic's. An example is a callback that puts a float in a `str` field.
5. **The returned value is `delivered`, unchanged.** Pydantic coercion and default-filling are unchanged.

The open shape is removed. The delivered value (`model_dump()` of the one ordinary validation) is validated against the declared types' **finite-only** structural shape, and **the call is rejected iff that validation reports a `finite_number` error at any position.**
- The shape is unchanged from rev 2 (callback-free, over delivered keys).
- **A union some finite-only alternative accepts reports nothing.** The complete-value union semantics and the `Any`/`object`/extra keeps are unchanged.
- **A non-finite value in a numeric position always reports `finite_number`.**

- **A position outside the declared shape reports only its own mismatch** (`string_type`, `float_parsing`, ...). That neither rejects the call nor exempts any other position.

## Revision 4: `L0506-D001-I002`, numeric-looking strings (final-review finding)

- **Trigger.** Codex's §11.8.8 final complete review (`#200`, code `8f6400a5` / docs `f352ff92`) returned CHANGES REQUIRED with `L0506-D001-I002`: CONTRACT_ASSURANCE_DEFECT, blocking.
  - A callback that delivers the **string** `"Infinity"`, `"-Infinity"` or `"NaN"` in a declared `float` field was rejected.
  - The rev-3 shape's lax `float` *coerced* the string to a non-finite float and reported `finite_number`.
  - The accepted baseline `3c15b057` delivers those strings unchanged.
- **Accepted.** I001 stays PROVISIONALLY_CLOSED on its own witnesses. Revisions 1–3 are kept as written.

### Root cause

Rev 3 assumed that a `finite_number` error means the delivered value holds an actual non-finite number. That holds only when the shape's numeric leaves do not coerce. Pydantic's lax `float` parses numeric strings, so a delivered string was judged as the number it spells.

### Revised rule: strict numeric leaves

The shape's numeric leaves are **strict**, so `finite_number` is reported **only for an actual runtime non-finite float** in a numeric position:
- a declared `float` becomes `Annotated[float, AllowInfNan(False), Strict()]`. A strict float still accepts an actual `int`;
- a declared `int` becomes `Annotated[int, Strict()] | <that float>`. An actual int passes, and an actual non-finite float a callback delivered there reports `finite_number`, as in rev 3.

Everything else in rev 3 is unchanged:
- one ordinary validation, and the delivered value returned unchanged;
- callback-free shapes;
- complete-value unions;
- any `finite_number` rejects;
- out-of-shape positions report only their own mismatch.

A delivered string reports `float_type`/`int_type` (out of shape), never `finite_number`. It is delivered unchanged, and it never exempts a sibling.

Probe (pydantic 2.13.4) on the strict finite `float`:
- ±inf and NaN → `finite_number`;
- `"Infinity"`, `"NaN"` and `"1"` → `float_type`;
- `1`, `-0.0` and `1e308` → pass.

`float | str` keeps the strings, and `list[float] | list[Any]` still keeps `[inf]`.

### Evidence (prototype `proto/l0506-ce-i001-rev2` @ `0b39d1731a83710de60c7e6e368faf9f57cedf3f`, evidence only)

**New real-pipeline witnesses** (`test_prepared_runtime_callbacks.py`), each for `"Infinity"`, `"-Infinity"`, `"NaN"`, plus the controls `"outside"` and `"1"`:
- a field after-validator delivering the string in `number: float` is accepted, and the hook and `execute` receive the original string;
- strings delivered in a `float`, an `int`, a `list[float]` element and a nested record's `float` are all delivered unchanged;
- a string in `float`/`int`/`list[float]`/`float | str` beside a **genuine** callback-produced ±Infinity/NaN `float` sibling is **rejected**. The string never exempts the numeric sibling.
